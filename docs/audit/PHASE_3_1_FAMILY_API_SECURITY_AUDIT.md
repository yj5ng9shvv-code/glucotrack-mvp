# PHASE 3.1 FAMILY WATCH API SECURITY AUDIT

Date: 2026-08-02
Mode: audit only (static code review; no application code, tests, schema, workflow,
commit, or push changes)

## Summary

**PHASE 3.1 STATUS: FINDINGS**

The repository has two independent Family API surfaces:

- legacy `/family/*`, backed by `family_links`;
- new `/api/family/*`, backed by the Family Security foundation tables.

JWT authentication is applied before both authenticated surfaces and rejects absent,
invalid, expired, and invalid-signature tokens with `401`. The new Family adapter has
two authorization findings that must be resolved before it is used for caregiver
management: a caregiver can revoke arbitrary members in its group, and domain access
errors are returned as `500` instead of the required `403`.

No Family Watch location or SOS API is implemented yet. Existing SOS routes are the
separate QR SOS-card feature, not Family Watch SOS.

## Authentication findings

- `authGuard` (`server.js:1176-1184`) requires a `Bearer` token and returns `401`
  for missing, invalid, expired, or wrongly signed JWTs.
- JWTs are generated by `authPayload` (`server.js:1203-1211`) with an expiry default
  of `30d` and verified with the configured secret.
- `jwtSecret` (`server.js:2010-2013`) fails server startup if the secret is absent or
  shorter than 32 characters. This is fail-safe configuration behaviour, not a
  request-level `401` response.
- The default 30-day token lifetime is long for a medical application. This is a
  **LOW** risk configuration consideration, not an observed bypass.

## Authorization and IDOR findings

### HIGH — Caregiver can revoke arbitrary Family members

`DELETE /api/family/member/:id` obtains a group through `getFamily(req.user.id)` and
calls `removeMember(family.id, req.params.id)` without confirming that the caller is
the group's patient/owner. Since `getFamily` accepts any active caregiver
(`familyService.js:11-15`), a caregiver can provide another member ID in the same
group, including the patient's membership, and revoke it.

Evidence:

- `backend/family/api/familyRoutes.js:10`
- `backend/family/services/familyService.js:11-15`
- `backend/family/repositories/familyRepository.js:9`

Expected result: `403` for a caregiver attempting member removal.
Current static result: mutation is permitted if the target ID belongs to the group.

### MEDIUM — Access-denied Family errors are returned as 500

`getFamily` throws `FamilyAccessDeniedError("ACCESS_DENIED")` for a non-member
(`familyService.js:11-15`). The router forwards it to Express, but the sole global
error handler returns `500 {"error":"internal server error"}` for this error
(`server.js:1162-1169`). Thus a stranger's `GET /api/family` does not return the
required `403`.

Expected result: `403`.
Current static result: `500`.

### Legacy Family IDOR review

The legacy read endpoint filters both `owner_user_id` and `caregiver_user_id`
(`server.js:955-965`), and legacy member revocation filters both link ID and owner
ID (`server.js:932-938`). No direct legacy IDOR was observed in those queries.

## Invitation security

The new invitation service uses `randomBytes(24)` and persists only a SHA-256 hash
(`familyInvitationService.js:2-15`). Acceptance requires the pending hash, recipient
email, unexpired status, and a different accepting user. This is a sound foundation.

The service checks expiry in application logic; its repository query does not filter
expiry, but the service rejects an expired record before membership is added.

The legacy invitation API retains `family_links.invite_code` in plaintext and returns
it to the owner (`server.js:858-898`, `server.js:1521-1531`). The code is recipient
email-bound, reducing impact, but plaintext persistence is a **MEDIUM** secret-handling
risk compared with the new hashed invitation model.

## Location security

`location_grants` is linked to both the patient and a Family member and has active,
revoked, and expired states (`025_family_security_foundation.sql:58-72`).

- Location grant creation is not connected to an API
  (`familyLocationService.js:1`).
- Revocation repository operations accept only a member ID; no public route currently
  exposes them.
- There is no dedicated grant action/audit table or actor identifier.

Result: no current HTTP location authorization bypass was found because no Family
location endpoint is implemented; the required ownership and audit policy must be
implemented before Phase 3.2 exposes location data.

## SOS security

No Family Watch SOS alert model or `/api/sos/*` Family endpoint exists. The existing
SOS implementation is a public QR SOS-card system:

- QR scan events may be created by anyone possessing the QR token
  (`server.js:439-459`), by design;
- scan coordinates are audit telemetry, but an untrusted scanner can submit arbitrary
  coordinates;
- profile updates and scan-history reads are bound to `req.user.id`
  (`server.js:556-590`).

Result: Family-specific "create/cancel/read foreign SOS" controls are **NOT
IMPLEMENTED**, so they cannot be marked verified. QR SOS scan integrity is a
**MEDIUM** design risk if scan locations are later used as trusted medical or safety
events.

## Security risks

| Severity | Finding |
| --- | --- |
| CRITICAL | None observed in the static audit scope. |
| HIGH | Active caregiver can revoke an arbitrary member of the same new Family group. |
| MEDIUM | Non-member Family requests receive 500 rather than 403. |
| MEDIUM | Legacy invite codes are stored in plaintext. |
| MEDIUM | Family Watch location and SOS authorization APIs/audit trail are not implemented. |
| LOW | JWT default lifetime is 30 days; reassess for the production threat model. |

## Recommended fix plan

1. Require the Family group's patient/owner identity before any member removal,
   invitation creation/revocation, permission mutation, or location-consent mutation.
2. Map Family domain authorization errors to a stable `403` response; map invalid
   invitation/member errors to appropriate 4xx responses.
3. Add isolated authorization regression tests for caregiver member removal,
   stranger access, invalid/expired JWT, and invitation reuse in Phase 3.1.1.
4. Define an explicit Family Watch location-grant ownership and audit model before
   exposing any `/api/location/*` endpoint.
5. Design the Family Watch SOS model separately from public QR SOS cards, including
   patient ownership, cancellation authorization, read isolation, and event audit.
6. Plan migration of the legacy `family_links` invitation flow to hashed one-time
   tokens before treating it as a security-equivalent Family API.
